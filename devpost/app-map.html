Metric Mirage — App Map

A take-home guide to how the app works and where to change it. Snapshot of commit db368e4; the code may drift after this.

What it is, in four pieces

A single static web page that checks whether an overall success rate hides what happened inside each group. Everything runs in the browser; there is no server or database.

  • Data in: the fictional tutoring example, or a CSV read by src/csv/parse-csv.ts and checked by src/csv/validate.ts.
  • Math engine: src/engine/analyze.ts splits the overall change into a within-group effect and a mix effect, in exact fractions.
  • Formatting and wording: src/engine/format.ts decides how many decimals to show; src/engine/narrative.ts turns the result into the headline, finding, explanation and briefing.
  • Interface: React components in src/components/, with the page's only state in src/useInvestigation.ts.

Reference route: one decision from plan to proof

The rule "never nudge a correctly rounded number to make a sum work" is traced through three stops. This is a reference route; follow it at your own pace.

  1. devpost/spec.md, heading Display plan and formatting — format.ts. The plan: keep full precision, show 1 decimal, rise to 2–3 decimals if rounded figures don't add up, else show ≈ with a rounding note.
  2. src/engine/format.ts, search for choosePrecision. It tries 1, 2, then 3 decimals and returns the first precision where partsReconcile (rate + mix = net) and ratesReconcile (current − previous = net) both hold. Rounding itself is exact (roundScaled in src/engine/rational.ts), so no value is ever adjusted.
  3. src/engine/analyze.test.ts, test "displayed equation always reconciles unless explicitly marked approximate". It checks the displayed figures add up on 500 seeded random datasets, against an independent exact-fraction oracle.
Example: data where one decimal would contradict itself

Group A 1/20 → 9/38, group B 30/50 → 33/50. At one decimal the equation would read +10.6 − 7.1 = +3.4, which does not add up (10.6 − 7.1 = 3.5) even though each number is correctly rounded. The app shows +10.55 − 7.11 = +3.44 instead.

To change this, start here

  • Wording of the headline, finding, "two forces" sentence, decision note or briefing: src/engine/narrative.ts (tests in narrative.test.ts, story.test.ts, briefing.test.ts).
  • Labels for the example vs. uploads ("pass rate"/"site" vs. "success rate"/"group"): src/engine/terms.ts.
  • CSV rules and error messages: src/csv/validate.ts (tests in validate.test.ts).
  • Colors, type and spacing: src/styles/tokens.css (contrast is checked by tokens.test.ts).
  • The flagship numbers: src/data/tutoring-example.ts and public/metric-mirage-template.csv (a test keeps them identical).

A practice to reuse

Turn a value judgement into a rule a test can check. "Rounding must never look contradictory" became a precise rule in spec.md (escalate 1→3 decimals, then ≈), one function (choosePrecision), and one property test over many generated inputs. Writing the rule down before coding is what made the earlier "nudge by 0.1" proposal visibly wrong, and the property test is what keeps it right. The same move works for any requirement phrased as "never" or "always": state it as a checkable condition in the spec, then test it on many inputs, not just the demo case.
